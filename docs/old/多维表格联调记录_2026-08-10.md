## 踩坑记录（重要）

- **选择字段写入格式**：如上，写入用纯字符串/字符串数组，这是本次联调抓到的唯一阻塞性 bug。
- **应用身份建的 base 用户不可见**：所有者是应用，用户本人打不开链接，必须补链接分享或加协作者。本次选了 `tenant_editable` 链接分享（PATCH `/drive/v1/permissions/{token}/public?type=bitable`）。
- **孤儿记录风险**：联调期间后端曾基于"当时的库数据"写入、随后本地库被重置，导致远端出现无绑定映射的孤儿记录（已清理 3 条）。教训：本地库重置/重seed后要检查远端是否残留无 binding 的记录，清理用 `records/batch_delete`。
- **测试环境隔离**：依赖"未配置"语义的测试必须自行 purge 环境变量，模式参照文件内注释。
- **控制台编码噪音**：Windows cmd 下中文输出会变 GBK 乱码，仅显示问题；写文件/读 API 都是正常 UTF-8，别被吓到，必要时 `sys.stdout.reconfigure(encoding='utf-8')`。

踩坑记录（三层，按时间顺序）：

- **① 200861（发送失败）**：schema 2.0 废弃 `{tag:action}` 容器，按钮必须平铺进 `body.elements`。
- **② 200671 第一层（handler 崩溃）**：lark-oapi 模型类只收**单个 dict**——`CallBackToast({"type":..., "content":...})`，传 kwargs 会 TypeError，handler 崩 → 不回响应帧 → 客户端报 200671。
- **③ 200671 第二层（进程残留，最隐蔽）**：机器上残留了 3 个 ws_listener 进程（含旧代码版本），**飞书把回调在所有活跃连接间分发**，点落到旧进程必崩 → 时好时坏。教训：重启监听前先确认 0 残留（`wmic process where "name='python.exe'" get ProcessId,CommandLine /format:csv` 过滤 `feishu.ws_listener`），运行时日志应恰好一条 connected。
- **旧版卡片回传不支持长连接**；新版卡片平台的 `card.action.trigger` 走事件通道才行。lark-oapi 1.7.2 的 ws.Client 会丢弃 CARD 帧，别指望注册旧式 card handler。
- **旧卡片 URL 写死**：跳转地址在发卡时固化进卡片，改 `FEISHU_WEB_BASE_URL` 后须重新发卡才生效。
- **测试隔离**：子进程仅 purge `FEISHU_*` 不够——`grading/llm.py` 模块级 `load_dotenv()` 经 main 导入链重载 .env，须在项目模块 import 前把 `dotenv.load_dotenv` patch 成 no-op（见 test_feishu_card.py）。
- **启动姿势**：必须在 backend 根目录以模块形式 `python -m feishu.ws_listener` 启动；直接 `python feishu/ws_listener.py` 会 ModuleNotFoundError（`database`、`feishu.*` 等导入都相对 backend 根目录解析）。运行环境需已装 lark-oapi（requirements.txt 已声明，换 venv 后先 `pip install -r requirements.txt`）。
- **日志噪音不是故障**：`ERROR ... processor not found, type: im.message.message_read_v1`（及 `bot_p2p_chat_entered` 等）是飞书推送了我们未注册处理器的边缘事件，不影响卡片回调与消息回复，忽略即可。
